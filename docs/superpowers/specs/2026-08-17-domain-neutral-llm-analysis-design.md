# 领域无关的项目级 LLM 分析与 RFLP 增强设计

日期：2026-08-17

## 背景与问题

当前需求提交的自动补全流程固定使用 `urban-medical-aam-v1`，并通过
`seed_domain_pack_workbench` 把领域包里的患者、急救医生、飞行员、空管等内容写入
每个工作区。结果是牙刷项目也会出现飞行汽车利益相关方。当前的场景矩阵同样使用固定
的医疗飞行器维度；RFLP 则主要由每条已确认需求机械生成一组 R/F/L/P 节点，因此节点
少、接口少、关系简单。

这不是把多个 SQLite 文件合并读取的问题，而是默认分析流程把固定领域知识当成了每个
项目的输入。项目级数据库隔离仍然保留，但需要增加作用域标记和自动校验，避免未来的
状态复制或错误复用再次造成串项目。

## 目标

1. 新项目的自动分析只读取当前项目自己的需求输入、当前项目已有的人工修改和当前激活
   的 LLM 配置，不自动注入任何行业领域包。
2. 同一个项目内的多个需求可以互相串联，并通过利益相关方、场景、功能、逻辑组件、物理
   组件和接口形成完整追溯链；不同项目之间禁止建立任何引用或关系。
3. 由 LLM 根据当前需求自行识别系统名称、领域、利益相关方、关注点、利益相关方需求、
   场景、正式需求以及 R/F/L/P 架构候选。
4. 自动流程默认保持一次提交、一次分析、一次保存；不为不同分析视角重复发送同一份完整
   文本。
5. 场景生成不再固定为医疗飞行器的天气、空域、患者等维度；由 LLM 按当前领域生成正常、
   边界、异常、故障、恢复和人为操作场景。
6. RFLP 图至少展示利益相关方/场景到需求、需求到功能、功能到逻辑、逻辑到物理以及接口
   和关键关系，并保留来源需求追溯。
7. LLM 未配置、超时或返回无效结构时，不回退到飞行汽车或其他固定领域结果；页面明确显示
   “待 LLM 分析”或诊断信息。
8. 领域包仍可作为用户明确选择的高级能力，用于特定领域覆盖审计，但不参与默认项目初始
   化，也不能覆盖当前项目的 LLM 分析结果。

## 非目标

- 不在本次工作中训练新的模型或建立跨项目共享的知识库。
- 不把一个项目的人工利益相关方复制到另一个项目。
- 不要求一次 LLM 调用生成完整的详细工程设计；输出仍是候选模型，需允许后续编辑和确认。

## 设计

### 1. 项目作用域与数据流

所有自动分析入口统一经过 `WebFacade` 的项目作用域绑定：

```text
当前 URL / workspace_name
        ↓
当前 workspace/.rflp/model.db
        ↓
当前 workbench + 当前项目输入原文
        ↓
一次领域无关 LLM 分析
        ↓
当前 workbench 的 stakeholders / scenarios / requirements / rflp
```

在 workbench 中增加 `project_scope`，至少包含 `workspace` 和当前分析输入的哈希。保存边界
写入该字段；读取旧数据时若缺少字段，只在当前工作区首次加载时补齐。若已有作用域与当前
`workspace_name` 不一致，直接报告作用域冲突，不继续渲染或合并。

`merge=True` 只表示在同一个工作区内追加或重新分析输入，不改变工作区边界。数据库访问
继续使用 `workspace.path / ".rflp" / "model.db"`，不增加全局 workbench 表，也不从其他
工作区扫描利益相关方、场景或 RFLP 数据。

项目内关联使用带项目作用域的 ID 引用。写入关系、场景关联需求、需求追溯或 RFLP 分配
关系前，验证引用对象属于当前 `workspace`；任一引用指向其他项目或不存在的对象，都拒绝
本次保存并记录作用域错误。读取项目图时只从当前 workbench 的对象集合构建闭包，因此同一
项目内可以串联多个需求，跨项目不能通过 ID、名称或历史记录间接串联。

### 2. 领域无关的 LLM 分析契约

默认自动流程不再调用 `seed_domain_pack_workbench`、`_discovery_pack` 或固定
`urban-medical-aam-v1`。新增项目分析请求，使用当前项目输入和已有人工内容作为输入，系统
提示词只约束输出格式、候选状态、来源和工程分析任务，不包含任何飞行汽车、牙刷或其他
行业实体。换言之，提示词是协议约束，不是领域知识库。

一次请求返回一个对象，包含以下受约束的集合：

```json
{
  "system": {"name": "", "domain": "", "mission": ""},
  "stakeholders": [],
  "concerns": [],
  "needs": [],
  "requirements": [],
  "scenarios": [],
  "architecture": {
    "functions": [],
    "logical_components": [],
    "physical_components": [],
    "interfaces": [],
    "relations": []
  },
  "open_questions": [],
  "diagnostics": []
}
```

每个实体必须带稳定的候选 ID、`status`、`producer=llm`、置信度、来源区域或输入摘要；
关系只能引用本次响应中的 ID 或当前项目内已有的需求 ID。响应归一化时丢弃未知引用、
重复项和不完整项，并记录可读诊断。自动流程沿用当前产品约定，将合法 LLM 候选纳入当前
项目的工作台；用户仍可在需求检查中编辑或驳回。

为了控制 token 消耗，请求只发送当前项目必要的输入字段，不重复发送完整 workbench 的
派生 SVG、审计历史、旧领域包或其他项目数据。响应数量设置上限：利益相关方 12、关注点
24、需求 24、场景 16、RFLP 架构节点 48、关系 96。若模型超过上限，保留前序稳定项并
记录截断诊断。

### 3. 场景生成

场景由当前领域无关响应直接映射到工作台。每个场景至少包含标题、目的、参与者、前置条件、
步骤、预期结果、故障/异常处理、场景类型和关联需求 ID。场景类型由以下有限集合约束：

- `normal`：正常工作流
- `boundary`：边界条件
- `failure`：故障或资源不可用
- `recovery`：恢复、降级或人工接管
- `misuse`：误操作、滥用或不当使用

若用户已经手工创建或编辑场景，自动重分析不得覆盖这些 `producer=user` 的记录。LLM
自动场景只替换同一项目、同一分析输入哈希下的旧自动场景。没有 LLM 时不调用固定的
`generate_scenario_matrix`，页面显示场景“待 LLM 分析”，用户仍可手工新增场景。

### 4. RFLP 模型与图形

保留已确认需求作为 R 层的确定性骨架，再把 LLM 返回的架构候选映射为 F/L/P 和接口节点：

- R：正式需求，带 `claim_id`、来源区域和验证方式。
- F：完成需求所需的系统功能，带输入、输出、前后置条件和异常处理。
- L：逻辑组件或逻辑服务，带职责、依赖和分配关系。
- P：物理组件、软件/硬件部署单元或实际资源，带实现职责。
- Interface：接口/交换项，带方向、来源、目标和交换内容；接口通过关系连接到相应的
  F/L/P 节点。

生成器必须保证每个 R 至少存在一条 `satisfiedBy` 到 F，每个 F 至少存在一条
`allocatedTo` 到 L，每个 L 至少存在一条 `realizedBy` 到 P。LLM 未提供完整链路时，
只补齐缺失的最小确定性占位节点，不再用 `Python Service` 等与领域无关的物理名称冒充
真实架构；占位节点标记 `status=needs-analysis` 并在诊断中提示。

RFLP SVG 保留 R/F/L/P 四列，但增加节点类型、简短职责/接口摘要、关系标签和追溯标记；
节点数量按实际模型动态布局，避免只显示每条需求的一组重复卡片。下载的 JSON/SysML
同时保留这些属性和关系。

### 5. 失败与兼容

- LLM 未配置：保留规则解析出的明确原文角色和需求，不补充领域包内容；`auto_analysis`
  标记为 `waiting_for_llm`。
- LLM 超时或失败：当前项目保留原有人工内容，清理本次自动生成的临时结果，写入诊断；
  不污染其他项目，也不回退到默认领域包。
- 旧工作区中已经存在飞行汽车领域包生成结果：不自动删除历史记录；用户重新提交并分析
  后，只生成当前输入对应的新分析。已有旧结果在审计/历史中保留，但当前工作台不应再追加
  新的固定领域包记录。
- 显式领域包入口继续可用，但必须把 pack ID 作为当前操作参数写入审计，并只影响当前
  工作区和当前一次分析。

## 测试策略

1. 纯函数测试：给定“设计医用安全电动牙刷”的 LLM 夹具响应，结果包含牙刷相关利益
   相关方和架构节点，不包含患者、飞行员、空管、飞行汽车等固定内容。
2. 项目隔离测试：在两个工作区提交飞行汽车和牙刷输入，分别保存、重新加载和渲染；同一
   项目内的多个需求可以形成完整追溯闭包，但两边的利益相关方、场景、RFLP 节点、关系和
   审计记录不得交叉；伪造跨项目引用时保存必须失败。
3. 请求契约测试：默认自动流程只发起一次领域无关请求；请求 payload 不包含领域包、其他
   工作区数据或派生 SVG；输出上限和未知引用校验生效。
4. 失败测试：LLM 未配置、超时、无效 JSON、超限和关系引用不存在时，结果不注入默认
   领域数据，并生成明确诊断。
5. RFLP 测试：验证 R-F、F-L、L-P、接口关系、追溯属性和动态节点数量；确认缺失链路
   只产生 `needs-analysis` 占位节点。
6. 回归测试：现有显式领域包审计、手工场景、项目删除、导入导出和全量 Web 页面测试
   继续通过。

## 验收标准

- 在新项目中输入“设计一款医用安全电动牙刷”，点击一次提交并分析后，利益相关方、
  场景、需求检查和 RFLP 图均来自该输入的 LLM 分析，不出现飞行汽车模板内容。
- 切换到另一个项目后，页面只显示另一个项目自己的数据；刷新和重启服务后仍然成立。
- LLM 暂时不可用时，系统不会生成错误领域结果，页面能解释原因并允许稍后重试。
- RFLP 图不再只有少量重复的 R/F/L/P 卡片，至少能看到需求追溯、功能、逻辑组件、物理
  组件和接口关系；缺失内容会被标记而不是伪造。
