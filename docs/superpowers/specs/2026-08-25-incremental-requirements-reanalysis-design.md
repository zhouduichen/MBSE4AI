# 增量需求自动补全与全量重新分析设计

## 1. 目标

在保留现有需求工作台、SQLite 持久化、六个 LLM 分析块和项目隔离机制的基础上，完善新增需求后的自动分析能力。

每次新增需求后，系统必须自动识别和补充：

- 新增或受影响的利益相关方；
- 利益相关方的目标、交互、Concern 和 Need；
- 需求与利益相关方、Concern、Need 之间的追溯关系；
- 正常、边界、故障、恢复、误操作及领域相关场景；
- 受需求影响的功能、逻辑组件、物理组件和接口关系；
- 全项目覆盖缺口。

系统负责尽可能全面地考虑和自动补充内容。所有内容始终允许人工编辑，不设置硬锁。任何删除只能由人工触发，LLM、规则和后台任务都不得直接删除对象。

需求总览提供“重新分析全部需求”操作，使用户可以基于当前全部有效需求重新执行完整分析。

## 2. 产品原则

### 2.1 全自动补充

新增需求保存后自动触发分析，不要求用户再点击独立的 AI 分析按钮。明显的新对象、空字段和缺失关系可以自动写入当前工作台。

### 2.2 人工内容优先但不锁定

人工编辑后的内容仍可继续编辑。系统不使用 `locked` 或不可修改状态。合并时按字段记录最后编辑来源：

- 人工当前值不被后台静默覆盖；
- LLM 对人工字段的不同意见写入建议；
- 用户可以采用、忽略或继续修改建议；
- 纯机器字段可以在后续分析中自动补充或修正。

### 2.3 只允许人工删除

LLM 输出协议不提供删除操作。后台分析可以标记“可能重复”或“可能不再适用”，但不得删除对象或解除人工建立的关系。

删除由用户在界面中发起，必须先展示影响范围，再由用户确认执行。

### 2.4 幂等和可追溯

同一项目版本重复分析不得产生重复对象。每个自动结果必须保留来源需求、来源区域、模型、分析块、输入版本、置信度和分析理由。

### 2.5 轻量实现

继续使用现有 Workbench JSON、SQLite Repository、JobService 和 OpenAI-compatible/Ollama 适配器。首版不引入向量数据库、消息队列、工作流引擎或新的独立存储服务。

## 3. 范围

### 3.1 本次包含

- 新增需求自动增量分析；
- 后台全项目覆盖审计；
- 手动触发的全量重新分析；
- 稳定对象身份和确定性对账；
- 利益相关方完整性分析；
- 场景完整性分析；
- 人工编辑来源记录和建议变更；
- 人工删除、影响预览和恢复；
- 大项目分批分析；
- 任务版本保护、失败重试和项目隔离；
- Web、API、应用服务和测试闭环。

### 3.2 本次不包含

- 多人实时协同编辑；
- 基于 Embedding 的语义搜索或向量去重；
- 自动执行物理系统、仿真或测试代码；
- LLM 自动删除或自动批准删除；
- 新的登录、权限或组织级审批系统；
- 跨工作区共享利益相关方或场景。

## 4. 方案选择

考虑过三种方案：

1. 每次重新生成全量快照：实现直接，但容易重复并覆盖人工内容。
2. 只处理新增需求的增量补丁：成本低，但长期容易遗漏跨需求影响。
3. 快速增量分析加后台全项目覆盖审计：兼顾响应速度和完整性。

采用第三种方案。新增需求先处理受影响链路，随后对整个项目做覆盖检查。用户还可以通过“重新分析全部需求”强制重新运行完整六块分析。

## 5. 总体架构

现有六块分析和持久化设施继续保留，新增以下应用级组件：

### 5.1 `AnalysisTriggerService`

统一处理三种触发模式：

- `incremental`：新增需求后的快速分析；
- `coverage_audit`：增量分析后的全项目覆盖审计；
- `full_reanalysis`：用户点击“重新分析全部需求”。

该服务确定目标工作区、需求版本、输入哈希、分析配置和受影响来源区域，然后提交可恢复 Job。

### 5.2 `ProjectSnapshotBuilder`

构造分析所需的规范化项目快照，包括：

- 当前有效需求和结构化需求；
- 利益相关方及其目标、交互和别名；
- Concern、Need 和追溯关系；
- 当前场景和场景覆盖状态；
- 当前 RFLP/MBSE 架构索引；
- 人工字段来源；
- 人工删除登记；
- 项目和输入版本。

快照不包含派生 SVG、执行日志或与当前分析块无关的大对象。

### 5.3 `CoverageAnalyzer`

使用确定性规则计算覆盖缺口。领域包可以增加分析维度，但不能绕过核心覆盖项。

输出包括：

- 缺失的利益相关方类别；
- 缺少 Concern/Need 的利益相关方；
- 没有关联利益相关方的需求；
- 缺失或未判定的场景类型；
- 没有关联需求的场景；
- 缺少功能、组件、接口或验证关系的需求；
- 未分析的来源批次。

### 5.4 `ReconciliationService`

LLM 不直接写入 Workbench。所有 LLM 结果先进入 `ReconciliationService`，由它负责：

- 稳定身份匹配；
- 去重；
- 字段来源优先级；
- 正式 ID 分配；
- 关系端点映射；
- 人工删除抑制；
- 建议变更生成；
- 幂等合并；
- 变更摘要和审计记录。

这是自动分析结果写入当前模型的唯一入口。

### 5.5 `DeletionImpactService`

负责人工删除前的影响计算和删除事务。它不接收 LLM 调用，只接受明确的用户删除命令。

## 6. 分析流程

### 6.1 新增需求自动流程

1. 保存新增文本或文档并合并规则结果。
2. 绑定新的工作区输入哈希和 Workbench revision。
3. 保存 accepted 规则基线。
4. 构建增量快照，标记本次新增的来源区域和需求。
5. 执行受影响的分析块。
6. 每个块完成后由对账器合并，并把正式对象传给下一块。
7. 生成或刷新 RFLP/MBSE 派生模型。
8. 提交同一 revision 的全项目覆盖审计。
9. 覆盖审计只对实际缺口调用补充分析。
10. 保存新增、补充、建议和失败摘要。

### 6.2 全量重新分析流程

用户点击“重新分析全部需求”后：

1. 读取当前全部有效需求和人工编辑；
2. 构建不可变分析快照；
3. 强制执行系统范围、利益相关方、Concern/Need、需求、场景和架构六个分析块；
4. 对大项目按批次处理全部来源，不截断；
5. 将批次候选统一对账；
6. 执行全局覆盖审计；
7. 刷新派生模型；
8. 显示完整分析摘要。

全量重新分析不清空当前模型，不覆盖人工当前值，不自动删除。

## 7. 分析块依赖与请求契约

六个分析块按以下顺序执行：

1. `system_scope`
2. `stakeholders`
3. `concerns_needs`
4. `requirements`
5. `scenarios`
6. `architecture`

每个块必须收到上一块对账后的正式对象，而不是依赖模型在独立请求中重复猜测 ID。

### 7.1 公共请求字段

```json
{
  "analysis_mode": "incremental",
  "workspace": "project-a",
  "snapshot_revision": 12,
  "input_hash": "...",
  "delta_region_ids": ["region-1"],
  "current_entities": {},
  "coverage_gaps": [],
  "deletion_registry": [],
  "input_regions": [],
  "limits": {},
  "pack_guidance": {}
}
```

### 7.2 跨块正式引用

`concerns_needs` 请求必须包含对账后的正式利益相关方 ID。`scenarios` 请求必须包含正式需求和正式利益相关方。`architecture` 请求必须包含正式需求、场景以及已有架构索引。

### 7.3 LLM 操作集合

LLM 响应只允许以下操作：

- `upsert_entity`
- `add_relation`
- `enrich_fields`
- `propose_change`
- `flag_for_review`

Schema 不定义 `delete`、`remove`、`purge` 或等价操作。未知操作导致该分析块校验失败。

## 8. 稳定身份和去重

### 8.1 永久内部 ID

对象首次创建时获得永久 ID。后续需求版本、输入哈希、模型或名称变化不得改变该 ID。

### 8.2 匹配索引

每个对象维护内部匹配信息：

```json
{
  "id": "stakeholder-123",
  "match_keys": ["operator:运维人员"],
  "aliases": ["维护人员"],
  "source_requirement_ids": ["req-1"],
  "revision": 3
}
```

人工改名只更新显示名称并追加别名，不重新生成对象 ID。

### 8.3 匹配顺序

1. 永久 ID；
2. 已知别名和 `match_keys`；
3. 规范化名称与类别；
4. 来源需求及已有关系；
5. 确定性文本相似度；
6. 无法确定时创建新对象，并标记“可能重复”。

首版不使用 Embedding。中文和英文文本只做大小写、空白、标点、常见角色别名和领域包别名规范化。

### 8.4 类型匹配规则

- 利益相关方：类别、规范化名称和别名；
- Concern：利益相关方 ID、Concern 类别和规范化名称；
- Need：利益相关方 ID、规范化陈述和来源需求；
- Requirement：规范化陈述、主体、义务词和来源区域；
- Scenario：场景类型、主要目标、核心参与者和需求集合；
- 架构元素：层级、规范化名称和关联需求。

## 9. 字段来源和人工编辑

对象保持兼容的现有字段，并增加以下最小元数据：

```json
{
  "revision": 3,
  "last_editor": "user",
  "field_sources": {
    "name": "user",
    "goals": "llm"
  },
  "source_requirement_ids": ["req-1"],
  "suggested_changes": [],
  "review_hint": ""
}
```

没有锁定字段。字段来源只控制自动合并优先级：

- `user`：保留当前值；模型差异写入 `suggested_changes`；
- `llm`：后续分析可以修正或补充；
- `rule`：明确原文和确定性规则优先于模型推断；
- 空字段：可以由 LLM 自动补齐。

用户采用模型建议后，该字段仍记录为 `user`，因为最终决定来自人工。

### 9.1 利益相关方编辑

界面允许编辑名称、类别、描述、目标、交互、Concern、Need 和关联需求。

### 9.2 场景编辑

界面允许编辑标题、类型、描述、参与者、触发、前置条件、步骤、预期结果、故障、恢复、关联需求和关联利益相关方。

保存人工修改后 revision 加一，并使旧分析快照失效。

## 10. 利益相关方完整性分析

核心覆盖类别包括：

- 客户或系统拥有者；
- 最终用户；
- 操作人员；
- 运维人员；
- 系统工程和研发；
- 制造商和供应商；
- 监管、认证和审计；
- 外部系统；
- 环境和基础设施；
- 领域特有角色。

系统对每个利益相关方检查名称、类别、目标、交互、Concern、Need、关联需求、关联场景和接口交换。

缺少的对象、字段和关系自动补充。已有人工值不覆盖。

## 11. 场景完整性分析

核心场景类型包括：

- 正常；
- 边界；
- 故障；
- 恢复；
- 误操作。

覆盖审计还检查生命周期阶段、外部系统异常、人机交互异常、性能或容量边界、安全、信息安全和监管约束。

每个覆盖维度必须得到以下结果之一：

- 已有场景覆盖；
- 自动新增场景；
- 明确记录不适用及理由。

场景必须包含标题、类型、参与者、触发、前置条件、步骤、预期结果、故障或恢复处理、需求引用、利益相关方引用、来源和分析理由。

## 12. 人工删除、抑制和恢复

### 12.1 删除预览

删除前显示：

- 目标对象；
- 关联 Concern/Need；
- 关联需求；
- 关联场景；
- RFLP/MBSE 关系；
- 将解除的接口和交换流；
- 将一并删除或保留的依赖对象。

### 12.2 删除事务

用户确认后，在一个 Repository transaction 中：

1. 从当前有效模型移除目标；
2. 按已展示的删除计划清理引用；
3. 保存删除前快照；
4. 写入审计记录；
5. 写入人工删除登记；
6. 使派生 RFLP/MBSE 失效并重新生成。

### 12.3 人工删除登记

Workbench 增加轻量的 `deletion_registry`：

```json
{
  "entity_id": "stakeholder-123",
  "entity_type": "stakeholder",
  "match_keys": ["operator:运维人员"],
  "deleted_revision": 14,
  "deleted_by": "user",
  "snapshot": {},
  "impact": {}
}
```

后续分析命中相同对象时不得自动恢复，只生成“人工删除对象可能再次适用”的提示。

### 12.4 恢复

“已删除内容”区域允许用户恢复对象。恢复使用删除快照和当前有效引用重新对账，并生成新的 revision 和审计记录。

## 13. Web 与 API

### 13.1 需求总览

增加：

- “重新分析全部需求”按钮；
- 当前 Workbench revision；
- 当前分析模式；
- 六个分析块进度；
- 新增对象、补充字段、新增关系、建议检查和失败数量；
- 失败块单独重试；
- 分析批次和来源覆盖数量。

### 13.2 利益相关方页面

增加直接编辑、人工删除、来源需求、关联场景、建议变更和版本历史。

### 13.3 场景页面

保留现有完整编辑和删除，增加关联利益相关方、分析来源、建议变更和版本历史。

### 13.4 已删除内容

提供删除对象列表、删除原因、影响摘要和恢复操作。

### 13.5 路由

建议增加：

- `POST /w/{workspace}/requirements/reanalyze`
- `POST /w/{workspace}/requirements/entities/delete-preview`
- `POST /w/{workspace}/requirements/entities/delete`
- `POST /w/{workspace}/requirements/entities/restore`
- 对应的 `/api/v1/workspaces/{workspace}/requirements/...` JSON API。

全量重新分析返回或跳转到 Job 状态，不阻塞 HTTP 请求等待所有 LLM 调用完成。

## 14. 并发、版本和幂等

每个分析 Job 绑定：

- workspace；
- snapshot revision；
- input hash；
- analysis mode；
- analysis configuration hash。

每个块合并前重新加载当前 Workbench 并校验 revision 和 input hash。

如果分析期间发生新需求或人工修改：

- 旧 Job 标记为 `superseded`；
- 旧结果不得写入当前 Workbench；
- 调度器合并重复请求，并为最新 revision 创建或保留一个目标 Job。

Job 幂等键为 workspace、revision、mode 和配置哈希。重复点击“重新分析全部需求”不得创建并行的同版本 Job。

## 15. 大项目处理

取消静默截取前 24 个输入区域或前 32 条需求的行为。

大项目使用分批分析：

1. 全部有效需求按稳定顺序分批；
2. 每批生成候选和覆盖发现；
3. 对账器统一分配正式 ID 并去重；
4. 执行项目级汇总和覆盖审计。

单次模型请求仍保留 token 和输出数量上限，但任何来源不得因上限被静默忽略。页面显示总来源、已分析来源、未分析来源和批次数。

## 16. 错误与降级

- 无 LLM：保存规则基线和人工内容，分析状态标记为 degraded；
- 单块失败：保留成功块和旧有效结果，只重试失败块；
- JSON 不合法：沿用一次结构修复，仍失败则记录诊断；
- 跨项目或不存在的引用：拒绝该条结果；
- 关系端点无法映射：不写入关系，记录诊断；
- 版本过期：丢弃旧结果并标记 superseded；
- 删除事务失败：整体回滚；
- 派生模型生成失败：保留对账后的 Workbench，标记派生模型待重试。

任何失败都不得清空已有人工内容或已保存的有效基线。

## 17. 测试策略

### 17.1 单元测试

- 各实体类型的稳定匹配键；
- 名称和别名规范化；
- 同一实体多次分析幂等；
- 人工字段优先；
- 纯机器字段可更新；
- 建议变更生成；
- LLM 删除操作被 Schema 拒绝；
- 人工删除登记阻止自动恢复；
- 删除影响计算和恢复。

### 17.2 应用与契约测试

- 各分析块收到上一块的正式 ID；
- 分析响应经过对账器才能写入；
- 版本过期结果无法合并；
- 重复全量分析复用幂等 Job；
- 分批分析覆盖全部来源；
- 项目作用域和关系端点校验；
- 部分失败保留成功块。

### 17.3 Web 和端到端测试

- 新需求自动出现新利益相关方、Concern/Need 和场景；
- 新需求补充已有利益相关方且不重复；
- 人工编辑利益相关方后重新分析不覆盖；
- 人工编辑场景后重新分析不覆盖；
- 全量重新分析按钮启动完整 Job；
- 删除前显示影响预览；
- 人工删除后全量分析不自动恢复；
- 已删除内容可以恢复；
- 两个项目并行分析仍完全隔离；
- 超过旧截断上限的需求全部被分析。

## 18. 验收标准

1. 新增涉及新角色的需求后，系统自动创建利益相关方及其 Concern/Need。
2. 新需求涉及已有角色时，系统补充缺失信息而不创建重复角色。
3. 新增需求自动生成缺失场景，并正确关联需求和利益相关方。
4. 系统检查五类核心场景；不适用类型保留明确理由。
5. 系统自动检查需求对功能、组件和接口的影响。
6. 人工修改利益相关方后，增量和全量分析都不覆盖人工当前值。
7. 人工修改场景后，增量和全量分析都不覆盖人工当前值。
8. 所有内容始终可继续人工编辑，没有硬锁。
9. 纯机器字段可以被后续分析自动补充或修正。
10. LLM 和后台任务无法执行删除。
11. 人工删除后，重新分析不会自动恢复同一对象。
12. 用户可以从已删除内容中恢复对象。
13. 连续执行两次全量重新分析不会产生重复对象或关系。
14. 分析期间发生人工编辑时，旧 Job 不能覆盖新 revision。
15. 超过旧输入上限时，所有需求来源都被处理。
16. 任一分析块失败时，已有模型和人工内容不会丢失。
17. 不同工作区之间不能共享或引用利益相关方、场景和架构对象。
18. 页面可以查看分析进度、覆盖情况、建议、删除影响和审计来源。

## 19. 实施分期

### 第一阶段：身份与对账基础

- 稳定内部 ID、匹配键和别名；
- 字段来源和人工优先合并；
- `ReconciliationService`；
- 幂等和人工编辑保护测试。

### 第二阶段：自动增量分析

- `AnalysisTriggerService` 和 `ProjectSnapshotBuilder`；
- 新增需求自动触发；
- 跨分析块正式 ID 传递；
- 利益相关方、Concern/Need 和场景自动补充；
- `CoverageAnalyzer`。

### 第三阶段：全量重新分析与任务安全

- “重新分析全部需求”按钮和 API；
- revision、input hash 和 superseded Job；
- 大项目分批；
- 全量覆盖摘要和失败块重试。

### 第四阶段：完整人工操作

- 利益相关方直接编辑；
- 场景来源和建议区；
- 删除影响预览；
- 人工删除登记；
- 已删除内容恢复；
- 完整 E2E 回归。

每个阶段必须通过专项测试、架构边界测试和相关回归测试后再进入下一阶段。
