# MBSE4AI v0.2 方法论智能化重构设计

> 本文是用户提供的《MBSE4AI v0.2 方法论智能化重构执行规范（Codex 执行版）》在仓库内的设计镜像。该规范是本次工作的需求来源；文中“必须/禁止”均按原规范解释。

## 目标

在不替换现有 ModelGraph、Patch、Revision、Gate、Repository 主链的前提下，使同一个模型在 MBSE4AI Harness 中执行 MBSE 时具备可审计的方法论提示、可执行的结构校验、谓词感知的追踪门禁、局部语义修复、声明式任务流程和有预算的上下文规划。

## 架构

主链保持：

```text
TaskSpec + Context + actual Prompt
        ↓
LLM / Rule Runtime
        ↓
TaskExecutionResponse / Patch
        ↓
methodology validators
        ↓
domain / PatchPolicy / endpoint validation
        ↓
CAS append_patch
        ↓
predicate-aware Gate + Coverage Matrix
        ↓
Issue → minimal RepairTask → re-gate
```

新增职责使用独立模块承载：PromptRegistry/resources、validators、trace/coverage、repair planner/strategies、completion、context planner。WorkflowRunner 仅编排状态、持久化和路由，不吸收这些领域判断。

## 阶段范围

1. PR-01：为 23 个 TaskSpec 提供独立、版本化、可哈希的 Markdown Prompt，并把实际内容写入请求与台账。
2. PR-02：在 response→patch 与 CAS 之间执行 schema、identity、reference、evidence、semantic、patch-policy 验证，并保留 provider JSON Schema 校验。
3. PR-03：以合法 RelationPredicate 定义 R→F→L→P→V trace，输出稳定 Requirement Coverage Matrix，并让 Gate 使用该矩阵。
4. PR-04：把 Gate/Validator failure 转换为 Issue、根因和受限 RepairTask；配置运行时优先 LLM repair，RuleRuntime 仍提供明确 provenance 的离线 fallback。
5. PR-05：让 CompletionCondition 与 FailureRoute 真实影响 Step 和 Workflow 状态，且纳入 TaskSpec hash。
6. PR-06：以 P0–P4 分层规划实体、关系、trace、evidence、history，保证上下文无悬空端点并在预算下稳定裁剪；检索 query 由真实 gap 生成。
7. PR-07：将 Harness deterministic、LLM MBSE、Agent robustness benchmark 分轨，报告记录模型、方法论、Prompt、TaskSpec、commit 等元数据。

## 关键不变量

- LLM/Rule Runtime 永远不能直接写 Repository。
- Validator failure 必须发生在 revision 增长之前。
- relation 只能使用 RelationPredicate 词表，并通过 endpoint kind validation。
- locked/user_modified 实体不能被自动覆盖。
- placeholder fallback 使用 RULE/SYSTEM producer、candidate 状态、human-review provenance，不得单独使 Gate 通过。
- Prompt 缺失或空内容必须 fail fast，禁止退回模板 ID 或 generic placeholder。
- 所有新排序、hash、coverage 输出都必须稳定。
- 无 API key 时 RuleRuntime 与 Track A 仍离线、确定性可运行。

## 错误模型

方法论校验统一产生可判定 code：`schema_invalid`、`identity_conflict`、`reference_missing`、`relation_endpoint_invalid`、`evidence_missing`、`semantic_invalid`、`patch_policy_violation`、`cas_conflict`。Issue code 供 FailureRoute 和 RepairPlanner 使用；诊断保留详细实体/关系信息。

## 测试策略

每个阶段先添加 fault/contract tests，再实现最小代码；阶段结束运行新增测试、全量 pytest、compileall、architecture_metrics、lint-imports 和 Track A quick benchmark。所有 fault tests 断言失败发生前后的 revision 与 graph hash 不变。最终同步 `docs/DEVELOPMENT_STATUS.md` 与方法论版本。

## 明确不做

本轮不恢复旧 Concept/MDO、Project Bridge、仿真、MLflow、旧 Job/Baseline/TaskContract；不引入 LangChain/LangGraph、CAD、真实仿真、多 Agent 群或知识图谱数据库迁移。
