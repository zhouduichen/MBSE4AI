# 需求分析与 MBSE 用例辅助工程化设计

**日期：** 2026-09-01  
**范围：** 用户需求清单中的功能点 1.1、1.2  
**目标版本：** RFLP-Lite 0.1.x 后续增量版本

## 1. 背景与目标

当前项目已经具备 DOCX/PDF/OCR 解析、结构化需求候选、来源追溯、场景、Use Case、活动图、时序图、人工审核和 Web 工作台首版。但现有实现仍有四个关键缺口：

1. 需求抽取以逐段规则匹配为主，属性、跨段约束和隐含约束能力不足；
2. 需求履历和作战场景数据尚未形成正式、版本化的数据集接口；
3. MBSE 编辑主要覆盖名称、状态和场景文本，尚不能完整修改参与者、条件、分支和消息；
4. 验收脚本可能在金标准指标为零时仍返回通过，不能证明功能已经满足客户需求。

本设计严格落实以下原始需求，不扩展到总体设计或 CAD 阶段：

- 支持导入作战纲要、技战术指标 Word/PDF 文档；
- 利用 NLP 自动提取实体、属性及隐含约束；
- 将非结构化文本映射为 MBSE 标准需求条目；
- 建立需求追溯矩阵初版；
- 基于需求文本推荐典型作战场景的时序图和活动图框架；
- 支持人机交互修改。

## 2. 设计原则与硬约束

### 2.1 保持现有交互逻辑

不引入新的向导式主流程，不重排现有导航。用户仍按以下路径工作：

1. 在“开始项目”创建或进入项目；
2. 在“需求建模”粘贴文本或上传 Word/PDF；
3. 点击“提交并分析”；
4. 在现有利益相关方、场景、需求检查和 RFLP 页面查看、编辑和审核结果；
5. 在“MBSE 设计图”查看 Use Case、活动图、时序图和追溯矩阵。

新增能力通过扩展现有卡片、详情区和编辑表单提供。现有 URL、CLI 命令、API 成功响应的兼容字段和工作区数据迁移能力必须保留。

### 2.2 AI 只生成候选

- 显式需求、属性、约束和隐含约束均先进入候选状态；
- 规则能够直接定位原文的显式候选可沿用现有批量接受入口；
- 隐含约束不得批量自动批准，必须逐条人工审核；
- 缺少有效来源证据的 AI 输出不得进入正式需求和追溯矩阵；
- AI 不得自动批准需求基线或 MBSE 模型。

### 2.3 确定性与可审计性

每次分析保存文档哈希、数据集版本、模型配置、提示契约版本、输出哈希、来源区域、置信度、诊断和审核记录。同一输入、配置和固定模型响应必须得到相同的规范化结果。

### 2.4 局部失败不污染成功结果

文档解析、显式需求、属性约束、隐含约束、场景检索和 MBSE 生成分别形成独立分析块。单块失败时保留其他成功块，并允许从现有页面单独重试。

## 3. 总体架构

```text
Word / PDF
  → Document Intelligence
  → DocumentArtifact / DocumentRegion
  → Explicit Requirement Extraction
  → Attribute & Constraint Extraction
  → Implicit Constraint Inference
  → Requirement History Retrieval
  → Semantic Validation & Reconciliation
  → Human Review
  → Accepted MBSE Requirements
  → Traceability Matrix
  → Combat Scenario Retrieval
  → Use Case / Activity / Sequence Drafts
  → Human Edit & Impact Rebuild
```

沿用当前六块智能分析、持久化 Job、严格 JSON Schema、Typed DTO、语义校验、CAS 提交和失败块重试机制。新增能力通过窄端口和独立应用服务接入，不继续扩大 `WebFacade`、Web 路由或现有大型工作台模块的职责。

## 4. 领域模型

### 4.1 文档对象

`DocumentArtifact`

- `id`、`filename`、`media_type`、`sha256`；
- 文档版本、页数、解析器版本、解析状态；
- 父版本标识，用于同名文档更新后的影响分析。

`DocumentRegion`

- `id`、`artifact_id`、`page`、`kind`、`locator`；
- `text`、`bbox`、`confidence`；
- `heading_path`、`table_id`、`row_index`、`column_index`；
- 解析诊断和 OCR 标记。

现有字段保持兼容；新增版面字段均为可选字段，并通过工作台 schema 迁移补齐默认值。

### 4.2 结构化需求对象

`RequirementCandidate`

- `subject`：需求主体；
- `predicate`：应、必须、不得、支持等规范化动作；
- `object`：能力、对象或结果；
- `conditions`：触发、环境、模式和前置条件；
- `verification_method`：分析、试验、检查或评审；
- `priority`、`confidence`、`status`；
- `source_region_ids`、`producer`、`rationale`。

`RequirementAttribute`

- `name`、`value`、`unit`；
- `minimum`、`maximum`、`enum_values`；
- `applies_to_requirement_id`；
- `source_region_ids`、`confidence`、`status`。

`RequirementConstraint`

- `constraint_type`：性能、接口、环境、安全、时序、禁止或依赖；
- `expression`：规范化、可读的约束表达式；
- `explicitness`：`explicit` 或 `inferred`；
- `applies_to_requirement_ids`；
- `source_region_ids`、`rationale`、`confidence`、`status`。

属性和约束使用独立对象，避免继续把所有信息压入 `list[list[str]]`。为保持 API 兼容，旧 `entities` 和 `constraints` 字段继续作为只读兼容投影输出。

### 4.3 数据集对象

`RequirementHistoryRecord`

- 历史需求正文、结构化字段、属性和约束；
- 所属型号或项目的脱敏分类；
- 来源、版本、批准状态和适用范围；
- 与其他历史需求的追溯关系。

`CombatScenarioRecord`

- 场景名称、任务目标、参与者和系统边界；
- 前置条件、主流程、备选流程、异常和恢复流程；
- 适用条件、关联需求和来源；
- 数据集版本和审核状态。

首版数据集支持 JSON、CSV 和只读 SQLite 导入，与概念方案库保持一致的版本化、只读导入模式。数据集内容不得硬编码在 Python 中。

### 4.4 MBSE 用例对象

`UseCaseDraft`

- 系统边界、参与者、目标；
- 前置条件、后置条件；
- 主流程、备选流程、异常流程和恢复流程；
- 关联需求、场景模板和来源证据；
- 状态、修订和审核历史。

`InteractionStep`

- `sender`、`receiver`、`message`；
- `sort`：同步、异步、返回；
- `guard`、`branch`、`order`；
- 关联需求和来源场景。

活动图节点和时序消息从同一组 Use Case 流程步骤编译，避免两个图形产生不一致的业务语义。

## 5. 功能设计

### 5.1 文档自动捕获

保留现有 DOCX ZIP/XML 解析、PDF 文本提取、扫描 PDF 渲染和 RapidOCR。增强内容包括：

- 将标题层级附加到后续段落和表格区域；
- 保留 DOCX 表格单元格位置，不再只拼接成一行文本；
- 将 PDF 相邻文字按版面行和阅读顺序稳定分组；
- 混合型 PDF 按页决定文本提取或 OCR，不因一页有少量文字而跳过图片主体；
- 对空白页、低 OCR 置信度、异常页尺寸和截断内容保存诊断；
- 文档解析失败时不启动后续 AI 块。

### 5.2 显式需求、实体、属性和约束抽取

采用两段式处理：

1. 规则层识别规范性动词、数值、单位、范围、枚举、否定词和来源位置；
2. AI 层在严格 schema 下完成跨句合并、主体补全、属性归属和约束类型判断。

规则层结果和 AI 层结果进入统一协调器进行去重和冲突检测。不能按“每个非空段落就是一条需求”生成正式候选。一个区域可以产生多条需求，多区域也可以合并为一条需求，但所有参与区域必须保留。

### 5.3 隐含约束推理

隐含约束分析使用独立请求和独立审核队列。每条结果必须包含：

- 约束正文和类型；
- 被约束的需求；
- 至少一个有效原文区域；
- 推理理由；
- 置信度；
- 验证建议。

系统拒绝不存在的来源区域和不存在的需求引用。隐含约束始终设置 `bulk_approvable=false`。

### 5.4 需求履历检索

新增 `RequirementHistoryRepositoryPort` 和 `RequirementRetrieverPort`。首版提供确定性加权检索：规范化术语、数值范围、单位、谓词和对象分别计分。可选向量检索只能作为端口后的增强实现，不能成为基础安装的强制依赖。

检索结果用于：

- 推荐历史需求表达；
- 补充可能遗漏的属性和约束；
- 标记重复或冲突候选；
- 展示历史来源和相似理由。

历史需求不能自动覆盖当前文档，也不能绕过人工审核。

### 5.5 MBSE 标准需求映射与追溯矩阵

接受后的结构化需求映射到现有 MBSE requirement 实体，并生成以下关系：

```text
DocumentRegion derivedFrom Requirement
Requirement representedBy RequirementAttribute
Requirement constrainedBy RequirementConstraint
HistoricalRequirement similarTo Requirement
Requirement refinedBy UseCase
Requirement representedBy ActivityNode
Requirement representedBy SequenceMessage
```

追溯矩阵至少提供：

- 原文区域 × 需求；
- 需求 × 属性/约束；
- 需求 × Use Case；
- 需求 × 活动节点；
- 需求 × 时序消息。

矩阵显示未覆盖、孤立、来源缺失和失效关系，并沿用现有矩阵 SVG/JSON 输出能力。

### 5.6 作战场景检索与推荐

新增 `CombatScenarioRepositoryPort` 和 `ScenarioRetrieverPort`。检索输入只使用当前项目已接受需求、系统边界和参与者。结果按任务目标、参与者、条件、流程和需求覆盖率排序。

推荐结果包含：

- 正常场景；
- 与输入内容有关的边界或异常场景；
- 原始数据集中存在时的恢复场景；
- 推荐理由、命中数据集记录和覆盖需求。

系统不得为了凑齐固定数量而生成与输入无关的场景。

### 5.7 Use Case、活动图和时序图生成

Use Case 草案由已接受需求和已选场景模板共同生成。生成顺序为：

1. 确定系统边界和参与者；
2. 生成 Use Case 目标和条件；
3. 生成主流程、备选流程、异常和恢复流程；
4. 将流程编译为活动节点、分支和汇合；
5. 将具备发送方、接收方和消息的步骤编译为时序交互；
6. 建立需求到 Use Case、节点和消息的追溯关系。

缺少发送方或接收方的步骤保留为候选消息，不能伪装成已就绪时序模型。

### 5.8 人机交互修改

保持当前页面和卡片式流程，扩展现有编辑能力：

- 需求：编辑、合并、拆分、接受、驳回；
- 属性/约束：编辑、接受、驳回、修改归属需求；
- 场景：编辑参与者、条件、主流程、异常和恢复流程；
- Use Case：编辑系统边界、参与者、目标和流程；
- 活动步骤：编辑名称、顺序、条件、分支和需求关联；
- 时序步骤：编辑发送方、接收方、消息类型、守卫和需求关联。

编辑继续使用表单和结构化列表，不引入拖拽画布。图形仍由保存后的语义模型确定性重新渲染。

## 6. 变更传播与一致性

以下变更会使派生结果进入 `stale`：

- 文档内容或文档版本变化；
- 已接受需求正文、属性或约束变化；
- 场景参与者、条件或步骤变化；
- 数据集记录版本变化；
- 模型生成契约版本变化。

系统计算影响集合，只重建受影响的需求、追溯关系、Use Case 和图形。旧结果保留在审核历史中，但不得继续以当前模型展示。

## 7. 应用服务与端口边界

新增或扩展以下窄边界：

- `DocumentAnalysisService`：文档解析和解析诊断；
- `RequirementExtractionCoordinator`：规则和 AI 提取块编排；
- `RequirementHistoryRepositoryPort`：历史需求只读访问；
- `RequirementRetrieverPort`：历史需求相似检索；
- `CombatScenarioRepositoryPort`：场景数据集只读访问；
- `ScenarioRetrieverPort`：场景相似检索；
- `TraceabilityService`：关系生成、覆盖审计和矩阵查询；
- `UseCaseModelingService`：Use Case、活动和时序语义编译；
- `ModelImpactService`：失效标记和受影响范围计算。

Web 路由和 CLI 只负责参数转换与错误映射。现有兼容 `WebFacade` 可在迁移期间代理新服务，但不得承载新领域逻辑。

## 8. 现有交互兼容设计

### 8.1 “需求建模”页面

继续使用现有上传和“提交并分析”按钮。分析状态区增加以下块状态：

- 文档解析；
- 显式需求；
- 属性与约束；
- 隐含约束；
- 需求履历检索；
- 场景检索；
- MBSE 用例生成。

### 8.2 “需求检查”页面

在现有候选卡片中增加属性、约束、历史相似项、来源页码和原文定位。接受、驳回和编辑入口保持不变。

### 8.3 “场景生成”页面

继续使用折叠卡片。卡片增加模板来源、推荐理由、需求覆盖和结构化交互步骤编辑。

### 8.4 “MBSE 设计图”页面

继续使用现有视图切换。页面增加所选 Use Case 的结构化编辑入口；保存后重新渲染活动图、时序图和追溯矩阵。

## 9. 错误处理

- 不支持或损坏的文档：拒绝导入并返回可操作诊断；
- 低质量 OCR：保留区域但标记低置信度，不自动批量接受；
- LLM 未配置：规则抽取继续工作，AI 块显示等待配置，不生成虚假结果；
- LLM 超时或 schema 错误：当前块失败，其他块保留，最多执行一次受控修复；
- 无效来源引用：拒绝该条结果并记录诊断；
- 数据集不可用：需求分析继续工作，历史和场景检索块显示不可用；
- 数据集版本变化：已有检索建议和派生模型标记失效；
- 并发人工编辑：沿用当前 CAS 修订检查，陈旧写入返回冲突；
- 图形渲染失败：保留语义模型并使用现有 SVG fallback。

## 10. 验收设计

### 10.1 数据集

建立版本化验收集，至少覆盖：

- 正常 DOCX 段落；
- DOCX 表格中的指标；
- 数字 PDF；
- 扫描 PDF；
- 跨段落需求；
- 数值范围和单位；
- 禁止性、接口、环境和时序约束；
- 需要人工判断的隐含约束；
- 正常、异常和恢复作战场景；
- 一条需求对应多个模型元素，以及多个需求共同约束一个场景。

每个金标准对象保存来源区域、结构化字段、属性、约束、场景关系和预期追溯关系。验收数据不得只使用当前六行客户需求样例。

### 10.2 功能通过条件

1. 所有支持格式的验收文档均可解析或返回明确的文件级失败原因；
2. 每条正式需求、属性、约束和模型关系均可追溯到有效来源；
3. 显式需求抽取在金标准集上的 precision、recall 均不低于 0.90；
4. 实体、属性和显式约束抽取的 micro-F1 均不低于 0.85；
5. 隐含约束只作为候选，来源有效率为 100%，自动批准数为 0；
6. 需求追溯矩阵正确标识覆盖、未覆盖和孤立项；
7. 对金标准场景，推荐结果前 5 项至少包含一个正确场景模板；
8. Use Case、活动图和时序图通过 schema 与引用完整性校验；
9. 修改需求或场景后，受影响模型全部标记失效，未受影响模型保持当前；
10. 人工修改保存后，JSON、SysML 子集和 SVG 输出保持一致；
11. 未配置 LLM 时不得用固定模板冒充智能结果；
12. 完整回归测试必须在隔离用户级 LLM 配置的环境中通过。

### 10.3 验收状态修正

现有验收报告调整为两层状态：

- `smoke_status`：文档解析、基本对象生成和导出链路是否可运行；
- `formal_status`：只有提供金标准并满足全部质量门槛时才能为 `passed`。

当 precision、recall 或 F1 未达门槛时，`formal_status` 必须失败，不能再出现指标为零但总体通过。

## 11. 测试策略

- 文档适配器：DOCX/PDF/OCR fixture 和版面定位测试；
- 领域模型：属性、约束、来源和状态不变量测试；
- 提取协调器：规则/AI 去重、冲突和局部失败测试；
- 数据集适配器：JSON、CSV、SQLite 一致性和版本测试；
- 检索：固定 fixture 的排序、过滤和稳定性测试；
- 追溯：覆盖、孤立、无效引用和变更失效测试；
- MBSE：Use Case 到活动和时序语义的契约测试；
- Web/API：保持现有路径和交互行为的兼容测试；
- E2E：Word/PDF → 需求审核 → 场景 → Use Case → 图形 → 修改 → 失效重建；
- 验收：金标准指标必须参与最终状态判定；
- 回归：使用空 `RFLP_CONFIG_DIR` 隔离本机保存的模型配置。

## 12. 实施分解

本设计按四个可独立验证的增量实施：

1. 修正验收语义并建立金标准数据结构；
2. 增强文档版面、属性约束和隐含约束提取；
3. 接入需求履历库、作战场景库和确定性检索；
4. 完善 Use Case/活动/时序编辑、影响分析和端到端验收。

每个增量均保留现有 UI 和 API 兼容行为，完成单元、契约和 E2E 测试后独立提交。

## 13. 非目标

本阶段不包含：

- 总体布局生成和真实 CAE 集成；
- CAD 三维建模、二维工程图和公差标注；
- DFM/DFA 审查；
