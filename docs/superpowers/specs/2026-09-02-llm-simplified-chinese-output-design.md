# LLM 简体中文输出设计

## 目标

面向中国用户的 RFLP-Lite 所有 LLM 生成内容默认使用简体中文。无论用户输入中文、英文或混合语言，需求、场景、利益相关方、功能、架构说明、方案解释、分析结论和开放问题等自然语言字段都应以简体中文返回。

英文资料仍作为输入证据保留，不能为了显示中文而修改原文、文件名、来源定位或历史记录。

## 范围与不变项

纳入范围：

- 需求分析与隐含约束建议；
- 项目分析的系统、利益相关方、关注点、需要、需求、场景和架构结果；
- 概念方案、参数建议、候选生成和覆盖缺口补全；
- JSON 修复请求中的重新生成内容。

保持原样：

- JSON 字段名、内部 ID、来源区域 ID 和哈希值；
- 固定枚举值和协议值，例如 `normal`、`failure`、`inferred`；
- 型号、标准编号、接口名称、代码标识、单位和必要的专有名词；
- 用户输入的英文原文及其证据引用。

## 方案

在 LLM 适配层增加一条统一的系统指令，并注入到每次结构化 JSON 请求的 system prompt 前面：

> 面向中国用户输出。无论输入资料使用何种语言，所有自然语言输出字段必须使用简体中文；不得因为输入是英文而用英文回答。保留 JSON 字段名、ID、固定枚举值、型号、标准编号、单位和必要专有名词原样。

这样所有通过 `OpenAICompatibleModel.complete_json` 发出的请求都自动获得相同约束，不需要在每个业务模块重复维护完整文案。JSON 结构校验继续由现有 response schema 负责，中文要求只作用于自然语言字段，不改变协议结构。

旧的可注入 completion 回调路径会复用同一条中文指令，避免非标准调用绕过统一规则。JSON 结构修复请求也必须包含该指令。LLM 连接测试保留 `OK` 探活语义，不把探活文本当作业务内容翻译。

## 数据流

1. 业务模块按现有方式构造 `GenerationRequest`。
2. 适配层在发送前把统一中文指令与原有 system prompt 合并。
3. 模型根据英文或中文输入生成结构化 JSON。
4. 现有 JSON 解析、schema 校验、修复和业务合并流程保持不变。
5. 业务层继续保存英文原始资料和可追溯 ID；用户界面读取模型生成的中文自然语言字段。

## 异常与边界

- 模型偶尔返回英文时，不修改原始资料，也不重写 ID 或结构化字段；请求修复流程仍优先保证 JSON 合法性。
- 模型不应将固定枚举值翻译成中文，否则会破坏现有业务校验；提示词明确要求保留这些值。
- 领域包中的英文术语只作为指导输入，不应覆盖全局中文输出约束；必要的标准名、型号和专名可保留。
- 不增加独立的机器翻译服务，避免翻译过程破坏 JSON、来源引用和专业符号。

## 测试

- 适配器单元测试验证每次结构化请求的 system prompt 都包含中文输出约束。
- 修复请求测试验证二次请求仍包含中文输出约束。
- 旧 completion 回调路径测试验证传入的请求提示词包含中文约束。
- 使用英文输入的模拟响应验证中文生成字段能够按现有 schema 正常解析和合并。
- 运行现有 LLM、需求分析、概念工作流和 Web/API 测试，确认字段名、ID、枚举值、原始英文证据和追溯关系不变。

## 验收标准

给定英文需求资料，用户可见的模型生成自然语言结果使用简体中文；页面和 API 的 JSON 结构、内部 ID、来源引用、固定枚举值、英文原始证据以及现有 LLM 调用流程保持兼容。
