# AI4MBSE 稀疏需求智能补全与架构图生成设计

**日期：** 2026-08-11

**状态：** 用户已批准（2026-08-11）

**适用项目：** RFLP-Lite / AI4MBSE 0.1.0 后续演进版本

## 1. 目标

在现有 RFLP-Lite 仓库内增加一条低耦合、可配置、可审核的智能分析链路。用户既可以输入完整工程文档，也可以只输入一句模糊目标或若干零散想法。系统负责提出尽可能全面的利益相关方、场景、能力、需求和架构候选，执行覆盖与矛盾检查，经人工确认后生成可追溯的 MBSE 语义模型和确定性架构图。

首个端到端验收样例为：

> 设计一款城市医疗用途的飞行汽车。

系统不得把模型推断伪装成用户原始需求，也不得声称已经穷尽开放世界中的所有可能性。这里的“避免缺漏”定义为：领域包规定的每个分析视角和覆盖单元都必须得到 `covered`、`candidate`、`unknown` 或 `not_applicable` 之一的明确结论，不允许存在未评估单元。

## 2. 已确认的建设原则

1. 继续复用当前仓库，不另起一个重复项目。
2. 保留现有 Workspace、SQLite、审核门禁、版本、追溯、证据、RFLP 和 SVG 能力。
3. 不继续把功能堆入 `requirements_workbench.py`、`web_facade.py` 或 `routes.py` 等大型文件；新能力采用独立模块和薄集成层。
4. 核心字段稳定，领域字段由版本化领域包和 JSON Schema 声明；增加或修改领域字段时不改核心 Python 代码。
5. 大模型只生成候选、假设、澄清问题和分析建议，不自动批准需求、场景、架构或基线。
6. 图形来自已确认语义模型；禁止让不同图形各自调用大模型并形成互相矛盾的内容。
7. 默认本地部署；大模型、渲染器和后续外部工程工具均通过端口与适配器替换。
8. 保持轻量：不引入微服务、消息队列、前端构建链、通用工作流引擎或向量数据库。

## 3. 范围

### 3.1 本设计包含

- 文本、文件和零散片段的统一输入；
- 显式事实、模糊目标、假设和待澄清项的区分；
- 利益相关方发现、分类、去重建议和交换流候选；
- 生命周期、运行环境、正常/异常/极端/失效场景候选；
- 能力、运行需求、功能需求和技术需求候选；
- 功能、逻辑组件、物理构建模块和分配关系候选；
- 完整性、覆盖率、冲突、重复和孤立节点检查；
- 人工逐条审核及批量审核门禁；
- 环境图、利益相关方层级图、需求分解图、生命周期图、用例/场景图、功能分解/交互图、逻辑/物理分解和交互图；
- JSON、SysML-lite 和 SVG 输出；PNG/PPTX 通过后续同一输出端口的适配器提供；
- 城市医疗飞行汽车领域包作为首个复杂领域样例。

### 3.2 本设计不包含

- 真实飞行器适航认证结论；
- 自动批准正式需求或设计基线；
- 真实 CAD 几何生成、CFD/结构仿真或控制律设计；
- 对开放世界“绝对无遗漏”的保证；
- 多组织权限、实时协同编辑和公网多租户部署；
- 让 LLM 直接输出不可编辑的整页图片作为正式模型。

## 4. 方案比较与结论

### 4.1 方案 A：在现有大文件中直接扩展

交付速度快，但会扩大应用层、Web 路由和适配器的直接依赖。领域字段、提示词、审核逻辑和图形逻辑会混在一起，不满足长期可修改性要求。

### 4.2 方案 B：新建独立项目

边界最干净，但会重复实现工作区、文档解析、SQLite、审核、追溯、RFLP、Web UI、CLI 和测试基础，且现有数据难以迁移。

### 4.3 方案 C：同仓库渐进式解耦

保留稳定底座，在现有分层中增加独立的智能发现、覆盖检查和图形语义模块，通过端口接入大模型与渲染器，并用桥接器连接旧工作台。

**结论：采用方案 C。** 它同时满足复用、低耦合、渐进迁移和轻量化要求。

依赖方向固定为：接口层调用应用服务，应用服务只依赖端口和领域对象，适配器实现端口。新智能分析模块不得直接导入 `rflp_lite.adapters`。

## 6. 领域对象与扩展机制

### 6.1 稳定候选信封

所有 AI、规则或领域包产生的内容先进入统一候选信封：

```json
{
  "id": "candidate-...",
  "element_type": "stakeholder",
  "schema_version": 1,
  "pack_id": "urban-medical-aam-v1",
  "status": "candidate",
  "payload": {},
  "provenance": [],
  "assumptions": [],
  "confidence": 0.0,
  "producer": "llm",
  "content_hash": "..."
}
```

信封字段属于平台核心，不允许领域包覆盖。`payload` 必须根据 `element_type` 使用领域包中的 JSON Schema 校验。这样既保留类型约束，又允许不同领域增加字段。

### 6.2 来源与推断分级

每个候选必须属于以下来源之一：

- `explicit`：用户原文或文件明确表达；
- `derived`：由已接受事实通过确定性规则推导；
- `inferred`：大模型基于领域知识提出；
- `assumed`：为继续分析而显式设立的临时假设；
- `external_reference`：来自被批准的法规、标准或知识包。

`inferred` 和 `assumed` 不得被“接受全部明确项”操作自动批准。

### 6.3 语义元素

第一版支持以下元素类型：

- `mission`、`system_boundary`；
- `stakeholder`、`concern`、`need`、`exchange_flow`；
- `lifecycle_phase`、`transition`；
- `use_case`、`operational_scenario`；
- `capability`、`requirement`；
- `function`、`functional_flow`、`functional_scenario`；
- `logical_component`、`physical_block`、`interface`；
- `solution_candidate`、`risk`、`clarification_question`。

关系继续复用现有 `ModelElement`/`Relation` 持久化语义，并增加受控谓词：`interactsWith`、`exchanges`、`participatesIn`、`motivates`、`refines`、`satisfiedBy`、`allocatedTo`、`realizedBy`、`derivedFrom`、`conflictsWith` 和 `verifies`。

### 6.4 领域包

领域包是声明式 JSON 数据，不执行代码。每个领域包包含：

- 元素类型及扩展字段 schema；
- 利益相关方分析视角；
- 生命周期模板；
- 场景维度与等价类；
- 极端环境、故障、人因、法规、安全和网络安全检查表；
- 能力与需求分类法；
- 覆盖规则和优先级；
- 大模型提示片段，不包含密钥；
- 图形分组、标签和展示规则。

首个领域包 `urban-medical-aam-v1` 至少覆盖人员、医疗机构、运营组织、制造维护、起降基础设施、空中交通、道路交通、通信导航、能源、气象、救援、监管、保险、网络安全、公众和环境等利益相关方视角；场景维度至少覆盖天气、能见度、时间、地理环境、任务阶段、系统状态、医疗紧迫度、人因、外部事件和生命周期。

## 7. 智能发现流水线

流水线按独立阶段运行，每个阶段消费和产生版本化 JSON，不共享可变全局状态。

### 7.1 输入规范化

合并文本粘贴、文件和后续追加片段，保留 Artifact、TextSpan、页码、位置、哈希和录入顺序。系统提取显式任务、对象、指标、约束和不确定语句，但不丢弃原文。

### 7.2 种子模型

把输入转换为最小任务模型：目标系统、应用类型、主要服务对象、地点、显式限制和待澄清项。输入只有一句话时，种子模型仍可成立，但所有未给出的关键边界均标为 `unknown`。

### 7.3 多视角候选生成

大模型不通过一次超长提示生成全部结果，而按受控视角分别生成候选：

1. 利益相关方与关注点；
2. 环境和交换流；
3. 生命周期和运行用例；
4. 正常、异常、极端和故障场景；
5. 能力与需求；
6. 功能与功能流；
7. 逻辑组件、物理构建模块和候选方案；
8. 风险、冲突和澄清问题。

每次调用只接受限定 JSON Schema，记录模型、提示模板版本、输入哈希和响应哈希。

### 7.4 规范化与去重

确定性规则负责：

- 名称清洗和单位规范化；
- 稳定 ID 与内容哈希；
- 完全重复项合并；
- 近似重复项只生成合并建议，不静默合并；
- 冲突数值、互斥假设和不一致边界标记；
- 失去来源的孤立候选拒绝进入正式图。

### 7.5 覆盖与定向补全

覆盖引擎根据领域包建立矩阵。示例：

```text
生命周期阶段 × 场景类型 × 环境维度 × 系统状态
利益相关方类别 × 交互类型 × 关注点类别
需求类别 × 来源 × 验证方式
功能 × 输入/输出 × 异常模式
```

为避免组合爆炸，领域包使用等价类、必测组合和风险优先级，不对所有维度做无界笛卡尔积。未覆盖的高优先级单元触发一次定向补全；补全后仍无结论则生成 `unknown` 和澄清问题，不伪造答案。

### 7.6 人工审核

页面按候选集和来源分组显示：原始输入、推断理由、假设、相关对象、冲突、覆盖影响和建议操作。编辑已接受元素会增加修订号并使下游派生元素回到待复核状态。只有已接受元素可以进入正式语义图、RFLP 和正式导出。

## 8. 图形生成

### 8.1 原则

图形渲染分为两步：

1. 从已接受语义图构建与展示无关的 `DiagramSpec`；
2. 渲染适配器把 `DiagramSpec` 输出为 SVG、PNG 或 PPTX。

`DiagramSpec` 只包含图类型、节点、边、分组、泳道、层级、标签和来源 ID，不包含 SVG 坐标细节。布局算法和视觉主题属于渲染适配器。

### 8.2 第一批图类型

- 利益相关方层级图；
- 系统环境与交换流图；
- 需求分解图；
- 生命周期状态图；
- 运行分解/用例图；
- 运行场景顺序图；
- 功能分解结构；
- 功能交互图与功能场景；
- 逻辑分解架构与逻辑交互图；
- 组件—构建模块分配图/表；
- 物理交互图；
- 技术需求分解图；
- 跨视图追溯矩阵。

### 8.3 可读性与大模型无关性

相同的已接受模型、领域包版本、主题版本和布局参数必须生成字节稳定的 SVG。节点过多时按领域包分组拆图，并生成总览图和分组子图；不通过缩小字体把所有内容挤在一张图中。所有标签保留语义元素 ID，支持点击查看来源和审核状态。


Web 路由和 CLI 只调用两个门面：`IntelligenceService` 和 `DiagramService`。现有 `requirements_workbench.py` 通过桥接函数读取新链路已接受的语义元素，不承载新推理逻辑。

### 9.2 工作台状态迁移

工作台 schema 从 v2 升级到 v3，增加一个 `discovery` 顶层片段，默认包含：

```json
{
  "intake": {},
  "candidate_sets": [],
  "coverage": {},
  "accepted_graph": {},
  "diagram_specs": [],
  "diagnostics": []
}
```

第一版继续存储在现有工作台 JSON 中，不新增数据库表。只有真实项目样本证明状态体积或查询性能不足时，才拆分为独立表。

### 9.3 兼容策略

- v2 工作区自动迁移为带空 `discovery` 的 v3；
- 旧 RFLP、场景和 MBSE 导出保持可用；
- 新链路通过桥接器生成旧链路可消费的 Stakeholder、Need、Requirement 和关系；
- 新模块先旁路运行，验收通过后再替代现有简化推断函数；
- 不在本次改造中重写无关的总体设计、仿真、项目扫描和测试执行功能。

## 10. 错误处理与降级

- 未配置或不可用的大模型：规则、领域包检查表和人工录入仍可运行，页面标记 `degraded`；
- 大模型返回非法 JSON：执行一次受限修复请求，仍失败则保存诊断，不修改候选集；
- 领域包不合法：加载前 schema 校验并拒绝运行，旧版本继续可用；
- 候选冲突：同时保留并生成 `conflictsWith`，等待人工选择；
- 覆盖不足：输出覆盖缺口和澄清问题，不宣称完成；
- 审核修订过期：拒绝写入并要求刷新；
- 图形过密：拆分为总览和子图，记录布局警告；
- 渲染失败：语义模型和 JSON 导出仍可用；
- 单阶段失败：保留前序候选集和运行证据，可从失败阶段重试；
- 任何失败不得修改已批准 Baseline。

## 11. 安全、审计与隐私

- API Key 只从环境变量或现有安全配置读取，不进入数据库、页面、日志和导出文件；
- 每次模型调用记录提供商标识、模型名、模板版本、输入/输出哈希、耗时和状态，不保存密钥；
- 外部模型调用必须由用户配置启用；未配置时保持本地确定性链路；
- 用户上传文件继续使用现有大小、路径和类型限制；
- 领域包只允许声明式数据和受限表达式，不允许执行任意代码；
- AI 不能执行批准、删除基线或调用真实飞行器/医疗系统。

## 12. 测试策略

### 12.1 领域与契约测试

- 候选信封字段、来源分级和状态转换；
- 领域包 schema、核心字段覆盖保护和版本校验；
- 关系谓词、孤立节点、过期修订和审核门禁；
- 应用智能模块禁止导入适配器的 Import Linter 合同。

### 12.2 应用测试

- 一句话输入生成合法种子模型；
- 每个分析视角独立调用并产生 schema 合格候选；
- 完全重复确定性合并、近似重复只提示；
- 高优先级覆盖缺口触发定向补全；
- LLM 不可用时进入降级模式；
- 已接受元素编辑使受影响下游元素回到待复核。

### 12.3 图形测试

- 每种 `DiagramSpec` 的节点、边、分组和追溯 ID；
- 相同输入生成字节一致 SVG；
- HTML/XML 转义；
- 大图分组拆分和布局警告；
- 图形不读取未接受候选。

### 12.4 端到端测试

以“城市医疗用途飞行汽车”为输入：

1. 生成种子模型并保留原文；
2. 所有领域包分析视角都有明确覆盖状态；
3. 候选覆盖利益相关方、生命周期、正常/异常/极端场景、能力、需求、功能和组件；
4. inferred/assumed 候选未经确认不得进入正式模型；
5. 人工接受一组候选后生成环境图、生命周期图、场景图、功能分解图和逻辑架构图；
6. 所有正式图节点可追溯到已接受元素及其来源；
7. 替换为测试模型适配器时，无需修改应用代码；
8. 修改领域包扩展字段和场景维度时，无需修改核心 Python；
9. 旧工作区、旧 MBSE/SVG 导出和现有全量测试保持通过。

## 13. 实施分解

为控制风险，建设分为五个可独立验证的增量：

1. **语义核心与领域包：** 候选信封、来源、领域包 schema、城市医疗飞行汽车包和工作台 v3 迁移；
2. **智能发现与覆盖：** 稀疏输入、分阶段生成、规范化、覆盖矩阵、冲突和澄清问题；
3. **人工审核与旧链路桥接：** 候选审核、依赖失效、RFLP/MBSE 桥接；
4. **图形语义与 SVG：** `DiagramSpec`、首批架构图、拆图、下载和追溯；
5. **端到端体验与可替换输出：** Web/CLI/API 闭环、城市医疗飞行汽车验收、PNG/PPTX 适配器接口和文档。

每个增量必须独立通过其专项测试、Import Linter 和相关回归测试后才能进入下一增量。

## 14. 完成标准

当以下条件全部满足时，本设计完成：

- 用户可输入一句话、零散文本或工程文档并获得结构化候选；
- 候选明确区分原文、推导、模型推断、假设和外部依据；
- 领域包规定的分析视角不存在未评估单元；
- 利益相关方和场景不仅有名称，还包含角色、目标、交互、条件、异常、需求和追溯；
- 用户可审核、编辑和拒绝候选，任何 AI 结果都不能绕过门禁；
- 已接受语义模型可生成本设计列出的核心 MBSE 图，并保持跨图一致；
- 新领域、新字段、新场景维度和图形主题可通过配置或适配器增加；
- 新智能模块与外部大模型/渲染器低耦合；
- 现有工作区和核心 RFLP-Lite 功能无回归；
- 代码、测试和用户文档能够说明每个模块的职责、输入、输出和替换方式。
