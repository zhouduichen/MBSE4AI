# 项目管理与需求删除设计

## 目标

把“开始项目”从单个 workspace 的首页改成项目管理入口：用户可以管理多个项目，展开项目卡片查看项目下的需求，进入项目继续使用现有需求工作台，并安全删除当前需求。

## 已确认的产品行为

- 现有 workspace 直接作为项目，不新增独立 Project 表或第二套项目 ID。
- 项目管理首页列出所有受管项目，每个项目使用默认折叠的卡片展示。
- 卡片摘要显示项目名、需求数量、当前模型状态和最近活动信息。
- 展开卡片后显示该项目的当前需求列表；点击需求进入该项目的需求规划页面。
- 项目卡片仍提供进入项目和创建新项目的入口。
- 删除需求前必须二次确认。
- 删除需求采用“删除当前内容、保留审计历史”：删除当前需求及其自动生成的派生结果，但不删除项目目录、原始输入文件或审计事件。
- 删除后的历史需求在需求台账中以“已删除”状态保留，不再作为当前需求参与建模。
- 删除最后一条当前需求不会删除项目；项目回到“暂无需求”状态。

## 页面与路由

### 项目管理首页

`GET /` 不再自动选择第一个项目并展示其工作台，而是展示所有项目卡片。每张卡片使用原生 `<details>`/`<summary>`：

- 默认收起；
- 摘要显示项目名称、当前需求数、已接受数和模型状态；
- 展开内容显示当前需求列表；
- 项目名称和“打开项目”链接指向 `/w/{workspace}/requirements`；
- 需求行显示需求主体、谓词、对象、状态和稳定 ID，并提供“删除需求”；
- 空项目显示“暂无需求”和“输入第一条需求”。

现有 `/w/{workspace}` 继续作为单项目工作台首页，导航中的“开始项目”统一返回 `/`。

### 删除接口

增加 WebFacade 用例：

```python
delete_requirement(workspace_name: str, requirement_id: str) -> dict[str, object]
```

增加 Web 路由：

```text
POST /w/{workspace}/requirements/delete
```

请求只接受当前 `claims` 中存在的 Requirement ID；不存在或已经删除时返回业务错误，不产生写入。

## 删除数据流

1. 读取当前 workbench，定位 `claims` 中的 Requirement ID；同步移除对应的 `structured_requirements`、审核队列项和变更集影响项。
2. 依据 Requirement 的 `span_id/source_region_id` 判断是否仍被其他当前需求引用；只清理不再被引用的孤立输入片段及其自动发现候选，保留仍被其他需求使用的来源。
3. 删除由该 Requirement 生成的自动场景及其执行记录；手动场景不删除，只移除已删除的关联 ID，若不再关联任何需求则保留为手动场景。
4. 清空当前派生的 `rflp`、`draft`、`mbse`、`baseline`、`trace_links`、`trace_coverage` 和相关缓存状态，避免模型继续引用已删除需求；若仍有当前需求，基于剩余状态重新生成可用模型。
5. 通过事务保存新的 workbench，记录 `requirements.deleted` 审计事件，并在 requirement ledger 中写入删除状态和历史事件。
6. 返回项目管理首页；项目目录、profile、输入文件、运行记录和审计历史保留。

## 数据与兼容性

- 不改变既有 workspace 目录结构和 `scenarios` JSON 形状。
- 新增的 ledger 状态 `deleted` 只用于历史展示，不会进入 `current_ids`。
- 既有工作区无需迁移；项目列表继续由 `list_managed_workspaces()` 提供。
- 当前需求列表只展示未删除的当前 claims；历史“已删除”记录继续由项目需求台账展示。
- 删除操作通过 SQLite 事务完成；失败时 workbench、ledger 和审计记录一起回滚。

## 方案选择

### 方案 A：复用 workspace 作为项目（采用）

改动最小，现有项目文件、需求工作台、运行记录和路由都能复用；项目卡片只是对已有 workspace 的管理视图。适合当前本地单用户 MVP。

### 方案 B：新增 Project 实体和 workspace 映射

语义更完整，但需要新的表、迁移、项目 ID、项目重命名和删除策略，会把当前明确的 UI 需求扩大成数据模型重构。

### 方案 C：只在前端把当前 workspace 卡片化

实现最快，但无法可靠维护项目需求计数、删除审计和跨页面状态，且会继续依赖前端猜测数据，不采用。

## 测试验收

- 创建两个项目后，`GET /` 显示两张项目卡片，项目卡片默认收起。
- 展开项目卡片可以看到该项目的当前需求；点击项目或需求可以进入对应项目页面。
- 删除一条需求后，该需求不再出现在当前列表，自动场景和派生模型不再引用它。
- 删除后项目仍存在，需求台账出现“已删除”历史记录，并且审计事件包含 `requirements.deleted`。
- 删除最后一条需求后项目仍能打开并显示空状态。
- 删除不存在的 Requirement ID 不改变状态、不写入审计。
- 既有场景、需求工作台、API 和全量测试继续通过。
