# 需求文档保守切分设计

## 1. 背景与问题

`RequirementClauseSplitter` 当前把中文/英文逗号、分号、句号以及部分连接词都视为切分点。工程需求文档通常用逗号串联同一条完整语义句中的多个指标、条件和动作，这会产生大量缺少主语、条件或动作的破碎子句。

例如：

```text
设计一型中程侦察无人机，最大起飞重量不超过 650 kg，任务载荷至少 150 kg，通信中断 30 秒后自动返航。
```

应保留为一条完整句子，同时从整句中抽取全部数值指标。

## 2. 目标与非目标

目标：

- 降低切分产生的语义碎片，优先保留原始句子的完整语义。
- 保持 `RequirementClause`、`NormalizedMetric`、`ClauseAnalysis` 的公开结构和稳定 ID 机制不变。
- 继续从完整子句中抽取多个数值指标、单位和比较符。
- 对小数、英文单位、连续标点和空行保持稳定处理。

非目标：

- 不引入 LLM 或新的 NLP 依赖。
- 不改动需求详情、工作流持久化和 Web 展示数据契约。
- 不在本次修改中重写指标命名、需求分类或现有语义抽取器。

## 3. 方案

采用“硬边界切分”方案：

- `。`、`！`、`？`、`!`、`?` 和明确的换行作为切分边界。
- 逗号、分号不再切分。
- `并且`、`此外`、`以及`、`and`、`also`、`while`、`when` 不再切分。
- ASCII 句号仅在不属于数字小数且后面为空白或文本结束时作为边界，避免将 `0.032` 拆开；中文句号仍直接作为边界。
- 连续边界符合并处理，边界两侧的空白去除；非边界标点和原始句内文本保持不变。

该方案的取舍是：逗号连接的多个独立指标会共享一个 `RequirementClause`，但 `normalized_metrics` 会保留整句中的每个指标。因此不会丢失结构化数值信息，且优先避免生成破碎文本。

## 4. 数据流与兼容性

`split()` 继续按原有流程处理字符串或 `DocumentRegion` 序列：

1. 将输入转换为区域序列。
2. 对每个区域按新的硬边界规则生成完整子句。
3. 对每个完整子句执行既有指标抽取和分类。
4. 使用区域 ID、局部序号、规范化文本和指标生成稳定子句 ID。

`analyze()` 继续为每条完整子句创建临时 `DocumentRegion` 并调用现有候选需求抽取；整句中的所有 `NormalizedMetric` 继续生成对应的属性和约束。既有调用方不需要修改接口。

## 5. 测试策略

补充和调整 `tests/application/test_requirement_clause_splitter.py`：

- 逗号/分号连接的任务描述、多个指标和故障恢复动作最终保留为一条完整子句。
- 整句中仍能抽取所有数值指标，比较符和单位不变。
- `通信中断 30 秒后自动返航` 等条件动作不产生脱离上下文的残片。
- `0.032 m3`、`205000000 Pa`、`km/h` 等数值和单位不被句号规则破坏。
- 多句文本、连续标点、空行和多区域输入仍按硬边界产生稳定顺序。
- 重复输入仍产生相同的子句和分析结果。
