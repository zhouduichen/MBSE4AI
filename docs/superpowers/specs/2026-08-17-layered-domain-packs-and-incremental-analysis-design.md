# 分层领域包与增量需求分析设计

**日期：** 2026-08-17  
**状态：** 待用户审阅  
**前置：** `urban-medical-aam-v1` 领域发现包、当前项目级 LLM 分析流程

## 目标

解决当前本地 4B/9B 模型一次性输出过大的问题，同时保留跨行业项目的通用分析能力，并避免为每一个专业项目创建一个难以维护的细小领域包。

本设计采用四层正交组合模型：

```text
common-v1 通用 MBSE 基础包
    + 行业/任务包，例如 medical-v1、aviation-v1、automotive-v1
    + 工程学科包，例如 mechanical-v1、electrical-v1、software-v1
    + 少量场景扩展，例如 urban-medical-aam-v1
```

提交需求时先保存规则分析和可用的领域骨架，再以小块、可校验的模型任务补充结果。模型失败不应清空或阻塞已经可用的需求结果。

## 范围

### 本轮范围

- 将通用分析包与窄场景包分离；
- 首批提供少量、覆盖面大的行业包，覆盖医疗、航空/航天、汽车/移动、工业制造、能源/基础设施和软件/数据平台等常见项目；
- 允许一个项目使用一个基础包、零个或多个行业/任务包、零个或多个工程学科包和零个或多个场景扩展；
- 将现有医疗飞行汽车包重构为“医疗行业包 + 航空/AAM 扩展 + 组合配置”的参考实现；
- 在提交后先返回规则/领域包结果，再执行可观察的 LLM 补充任务；
- 将单次大模型调用拆成可独立校验、重试和合并的分析块；
- 用户明确输入、规则结果、领域包种子和成功的快速分析结果默认写入 `accepted`；
- 保留 `producer`、来源区域、输入哈希、领域包版本和诊断，支持后续追溯；
- 4B 模型失败时保留部分结果，并能显示失败块和重试入口。

### 非目标

- 不为每个具体产品或任务创建独立包；
- 不把领域包变成硬编码的最终答案或固定行业模板；
- 不强制所有项目启用医疗、航空等行业包；
- 不为每一个细分专业建立独立小包；优先通过行业包、工程学科包和场景扩展组合覆盖项目；
- 不在本轮实现远程分布式任务队列、跨机器 worker 或流式 token 展示；
- 不把模型推断伪装成客户原文或形式化验证结论。

## 当前问题与根因

当前普通项目流程在 `project_analysis.py` 中构造一个大型响应协议，要求一次返回系统、利益相关方、Concern、Need、需求、五类场景、RFLP 架构和关系。`OpenAICompatibleModel` 对本地模型还会把请求限制在 `local_max_tokens=3000`，任意一段 JSON 截断都会导致整次分析进入 `waiting_for_llm`。

当前 `JobService` 只记录同步操作，需求提交本身仍在 HTTP 请求内等待 LLM。结果是：规则分析已经可以保存，但用户在模型请求结束前看不到返回；如果模型失败，页面只显示“等待 LLM”，容易被理解为没有结果。

现有 `urban-medical-aam-v1` 包包含医疗飞行汽车的利益相关方、生命周期、场景维度、覆盖规则和提示片段。它适合作为组合扩展，但不应直接作为通用医疗包，也不应成为普通项目分析的默认包。

## 方案选择

### 方案 A：只扩大单次输出预算

改大 `max_tokens` 并增加 JSON 修复次数。实现简单，但会增加本地发热和等待时间；4B 仍可能在复杂关系或场景数组处生成不完整结果。本方案不采用。

### 方案 B：把完整领域包拼进单次 Prompt

比方案 A 能提供更多领域线索，但会进一步增加上下文和输出规模，仍然是“一个请求失败、全部结果失败”。本方案不作为主流程。

### 方案 C：分层领域包 + 确定性骨架 + 增量模型任务（采用）

领域包负责定义覆盖面、种子和任务模板；规则层先产出可用结果；LLM 只处理一个分析块，并逐块保存。该方案同时解决包的可维护性、模型输出完整性和页面无返回问题。

## 分层领域包模型

### 通用基础包

`common-v1` 负责跨行业的分析结构，不包含医疗、航空等具体对象。建议包含：

- 通用利益相关方视角：拥有者、最终用户、运营、工程、供应商、监管、外部系统、环境；
- 通用生命周期：目标定义、概念、系统设计、实现/制造、验证确认、运行维护、变更退役；
- 通用场景类型：正常、边界、故障、恢复、误操作；
- 通用需求分类：能力、质量属性、约束、接口、可验证性、运维；
- R/F/L/P 分层任务模板和基本覆盖规则；
- 每个分析块的 JSON schema、输出上限和验证策略。

### 行业/任务包

行业包提供跨多个产品的稳定知识，例如 `medical-v1` 应覆盖患者、医护、医院、临床安全、医疗设备、隐私、数据治理、医疗监管和交接流程。

首批行业包保持在少量宽覆盖集合内：

- `medical-v1`：医疗服务、临床流程、患者安全、医护角色、医疗数据和医疗监管；
- `aviation-v1`：飞行阶段、空域、导航、气象、能源、维护和适航；
- `automotive-v1`：道路交通、驾驶员/乘员、车辆功能、主动/被动安全、诊断和售后；
- `industrial-v1`：产线、设备、工艺、质量、维护、供应链和工业安全；
- `energy-infrastructure-v1`：能源供给、储能、并网、设施运维、可靠性和应急；
- `software-data-v1`：用户、服务、数据、接口、权限、可观测性、隐私和持续交付。

这些包只提供行业视角、词汇、覆盖维度、典型约束和任务模板，不直接生成某个具体项目的最终答案。新的项目如果只属于同一行业，不应再创建新的小包；只有出现稳定的跨项目交叉场景时，才增加组合扩展。

### 工程学科包

工程学科包与行业包正交，描述可跨行业复用的工程分析方法和对象。首批学科包包括：

- `mechanical-v1`：机构、结构、载荷、运动、材料、强度、疲劳、装配和维护；
- `electrical-v1`：供配电、储能、功率、信号、接地、EMC、保护和电气安全；
- `software-v1`：软件组件、服务、数据、接口、状态、部署、测试和可观测性；
- `control-v1`：感知、估计、控制回路、执行器、模式、故障降级和实时性；
- `thermal-v1`：热源、热路径、散热、环境包络、热保护和热失效；
- `safety-v1`：危害、风险、故障树、失效模式、独立保护、验证证据和安全论证；
- `manufacturing-v1`：工艺、质量、供应链、装配、检验、放行和维修保障。

学科包不复制医疗、航空或汽车的利益相关方清单；它们提供学科专属的 Concern、参数、接口、验证方法和覆盖规则。一个项目可以同时选择多个学科包，例如医疗飞行汽车可以组合医疗、航空、机械、电气、控制和安全，而不需要创建“医疗飞行汽车电气包”。

### 场景扩展包

场景扩展包只保存行业交叉处的增量内容。`urban-medical-aam-v1` 应重构为对 `medical-v1` 和 `aviation-v1` 的组合引用，并只保留医疗空中交通特有的映射、任务阶段、空域约束和特殊场景。

组合包不得复制父包的完整利益相关方列表；加载器负责合并、去重和记录每一项来自哪个包。`urban-medical-aam-v1` 仅作为医疗、航空和相关学科之间的场景组合扩展示例，不再作为唯一的医疗领域实现。

### 包接口

保持现有声明式 JSON 思路，新增组合元数据：

```json
{
  "id": "urban-medical-aam-v1",
  "version": 1,
  "extends": ["medical-v1", "aviation-v1"],
  "disciplines": ["mechanical-v1", "electrical-v1", "control-v1", "safety-v1"],
  "activation_terms": ["医疗飞行汽车", "空中医疗转运"],
  "stakeholder_lenses": [],
  "lifecycle_phases": [],
  "scenario_dimensions": [],
  "coverage_rules": [],
  "prompt_fragments": {},
  "mappings": []
}
```

`extends` 只表达组合关系，不允许覆盖核心身份、状态、哈希、来源或审计字段。`activation_terms` 只用于推荐或显式选择，不在弱匹配时强制套包。

## 提交与分析数据流

```text
提交输入
  -> 解析文档与规则抽取
  -> 选择 common-v1 + 行业/任务包 + 工程学科包 + 可选场景扩展
  -> 写入 accepted 的输入需求和确定性种子
  -> 立即返回需求工作台
  -> 创建 LLM 补充任务
  -> 按块生成、校验、重试、合并
  -> 更新模块状态和进度
```

### 第一阶段：确定性返回

- 解析输入、保留来源区域和哈希；
- 规则抽取明确需求、实体和可识别关系；
- 领域包种子按输入来源关联并标记 `producer=domain-pack`；
- 明确输入、规则结果和种子默认 `status=accepted`；
- 保存 `auto_analysis.status=baseline_ready`；
- HTTP 请求不等待模型，页面立即可见当前结果。

### 第二阶段：增量 LLM 任务

分析任务按以下块拆分，可根据包的覆盖规则启用：

1. 系统使命与项目范围；
2. 利益相关方和交互；
3. Concern / Need；
4. 可验证需求与验证方法；
5. 场景，按生命周期或场景维度分块；
6. R/F/L/P 功能、逻辑、物理节点；
7. 接口和关系；
8. 覆盖缺口补全。

每个块有独立 schema、输入哈希、领域包版本、最大项数和最大 token。块成功后立即持久化；块失败只记录该块的 `failed` 状态和诊断，不回滚已完成块。

## LLM 返回优化

### 小块协议

不再让本地模型一次性返回完整项目图。每个块只负责一种对象和有限数量的项：

- 系统范围：1 个对象，最多 500 output tokens；
- 利益相关方：最多 8 项，最多 1200 output tokens；
- Concern / Need：按利益相关方分块，每块最多 6 个利益相关方，最多 1400 output tokens；
- 需求：每块最多 8 条，最多 1600 output tokens；
- 场景：按生命周期或场景维度分块，每块最多 4 个场景，最多 1400 output tokens；
- R/F/L/P 节点与接口：按层分块，每块最多 10 个节点，最多 1600 output tokens。

实际请求的 `max_tokens` 取块预算和档案 `local_max_tokens` 的较小值；不再使用一个覆盖全流程的固定 3000 token 上限。4B 模型默认关闭思考轨迹、使用短上下文和小输出块，只有缺口补全才继续发起请求。

### 结构化输出与局部修复

- Ollama 原生接口优先使用每块的 JSON Schema `format`；OpenAI-compatible 接口使用 `response_format`；
- 解析顺序为原生 JSON、去围栏 JSON、对象边界提取；
- schema 校验失败时只对当前块做一次短修复，修复提示包含缺失字段和剩余项数，不重复发送完整项目上下文；
- 修复仍失败时，该块进入 `degraded`，使用规则/领域包结果，不把空数组视为成功；
- 每块记录 `request_id`、模型、输入哈希、输出哈希、token 预算、耗时和失败原因，便于定位 4B 的实际瓶颈。

### 结果先返回与幂等合并

规则/领域骨架保存后，HTTP 请求立即返回；LLM 补充使用独立 job。每个块的幂等键为：

```text
hash(workspace, input_hash, pack_hashes, block_id, block_revision, model_id)
```

重复刷新或重试不会重复添加同一项。模型块成功后以稳定 ID 合并，保留手工内容、规则内容和其他已成功块。页面显示已完成块、进行中块和失败块，不再只显示“等待 LLM”。

### 任务状态

复用现有 `.rflp/jobs.json` 记录格式并扩展：

```json
{
  "kind": "requirements-enrichment",
  "status": "running",
  "blocks": {
    "stakeholders": "succeeded",
    "requirements": "failed",
    "scenarios": "queued"
  },
  "model": "qwen3.5:4b",
  "domain_packs": ["common-v1", "medical-v1"]
}
```

本轮仍使用本地单进程 worker；页面通过已有 job JSON 端点读取状态。服务重启后，未完成块标记为可重试，不删除已保存结果。

## 输出完整性与降级

- 每个块先进行 JSON 解析，再进行 schema 和来源引用校验；
- 失败时仅对当前块发送一次短修复请求；
- 修复仍失败则使用领域包种子和规则结果作为该块的降级结果；
- 不把空数组或缺字段响应当作成功；
- 不清空上一版已成功的 LLM 结果，除非输入哈希发生变化且明确开始新版本；
- `auto_analysis` 显示 `baseline_ready`、`enriching`、`completed` 或 `degraded`，并展示失败块、错误原因和重试动作；
- 所有模型补充保留 `producer=llm`、`analysis_input_hash`、`project_workspace`、`model_id` 和 `provenance`。
- 领域包覆盖结果和模型补充结果分开统计；“基础结果可用”不再依赖所有模型块成功。

## 接受状态与审核

快速提交路径遵循“默认接受”约定：

- 用户明确输入：`accepted`；
- 规则解析结果：`accepted`；
- 领域包确定性种子：`accepted`；
- 快速分析成功的 LLM 补充：`accepted`；
- LLM 失败的块：不生成伪造候选，只保留降级结果和诊断；
- 用户显式编辑、驳回或隐含约束建议：仍保留单独的审核入口。

需求工作台可以继续显示来源、置信度、假设和理由，但不再要求用户先确认才能看到或继续使用结果。

## 配置与迁移

- 将 `analysis_config` 从单个 `domain_pack_id` 扩展为 `base_pack_id`、`industry_pack_ids`、`discipline_pack_ids`、`overlay_pack_ids`；`base_pack_id` 默认是 `common-v1`，旧字段和缺失配置都迁移为这个基础包；
- 行业包、工程学科包和场景扩展包通过项目设置显式选择，必要时提供基于 `activation_terms` 和输入术语的推荐；未选择覆盖包时仍使用完整的通用基础包，不回退到无包分析；
- 旧的 `urban-medical-aam-v1` 调用保持兼容；新组合加载器在没有 `extends` 时按旧格式读取；
- 已有工作区不删除现有结果，重新提交或重新分析时写入新的包组合和输入哈希；
- 旧的单次 `auto_analysis` 状态映射为 `baseline_ready` 或 `degraded`，不把历史失败误报为成功。

## 测试与验收标准

### 领域包

- `common-v1`、首批行业包、首批工程学科包和组合包均通过 schema 校验；
- 首批行业包能够覆盖医疗、航空/航天、汽车/移动、工业制造、能源/基础设施和软件/数据平台的常见分析视角；
- 首批工程学科包能够覆盖机械、电气、软件、控制、热、系统安全和制造保障的常见分析视角；
- 组合包合并后无重复稳定 ID，父包来源可追溯；
- 独立医疗项目不会自动注入航空对象；医疗飞行汽车组合能同时获得医疗和航空覆盖；
- 包版本或组合关系变化会进入输入哈希和审计记录。

### LLM 分析

- 小模型返回截断 JSON 时，已完成块仍然可见；
- 4B 模型在每个块的输出预算内能够返回合法 JSON；
- 单块失败不会清空规则需求、领域种子或其他成功块；
- 重试只影响失败块，不重复生成已经成功的块；
- 4B 模型的每个请求都受项数和 token 上限约束；
- 空响应、非对象响应、错误来源 ID 和缺失必填字段均被标记为失败。

### Web / 工作台

- 提交后在不等待模型的情况下立即看到已接受的需求；
- 页面显示 enrichment job、每个块状态和失败原因；
- 服务重启后可以继续查看已有基线，并重试未完成块；
- 默认接受的需求不会出现在待确认队列；
- 旧工作区和现有 API/CLI 调用保持兼容。

## 实施顺序

1. 先实现通用包/行业包/工程学科包/组合包的数据契约和加载迁移；
2. 建立首批宽覆盖行业包，避免复制窄场景包内容；
3. 将医疗飞行汽车包拆为组合配置，补齐通用医疗和航空基础包；
4. 把规则与领域种子阶段从 LLM 请求中分离，提交后立即保存；
5. 实现分块分析、结构化输出、局部重试、降级和幂等任务状态；
6. 改造 Web 状态展示和重试入口；
7. 更新默认接受逻辑和历史工作区迁移；
8. 用 4B 模型、截断/空响应 fixture、行业组合包和通用项目 fixture 做端到端验证。
